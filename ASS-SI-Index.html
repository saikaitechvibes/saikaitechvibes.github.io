01 · Foundations

What is Azure AI Search & why do we need it?

Azure AI Search (formerly "Azure Cognitive Search / Azure Search Service") is a fully managed search-as-a-service. You push data into an index - a search-optimized copy of your DB data - and query it with rich full-text, filter, sort, facet and AI capabilities.

The problem it solves

  • Relational LIKE '%term%' queries don't scale and can't rank by relevance.
  • Users expect Google-like search: typo tolerance, synonyms, partial matches, ranking.
  • Data lives across SQL, Cosmos DB, Blob, APIs - you need one queryable surface.

What an index gives you

  • Inverted index for millisecond full-text search over millions of docs.
  • Relevance scoring (BM25) out of the box.
  • Filters, sorting, facets, suggestions & autocomplete.
🧭

Mental model

Think of the index like a book's index at the back: instead of reading every page (row scan), you jump straight to the pages (documents) that contain your term - pre-computed and ranked.

Core building blocks

Why not just a database?

A database is optimized for transactions & exact lookups. A search index is optimized for language, relevance, and read-heavy discovery. They complement each other - the DB is the system of record; the index is the query surface.

02 · Data Hygiene

Why lower-case (normalize) string fields?

Two different behaviours are at play - full-text search (already case-insensitive) vs filters ($filter, which are case-SENSITIVE and exact). Normalizing to lower-case on ingestion protects you from the second trap.

The trap: filters are exact & case-sensitive

// Document stored as "Active"
$filter=status eq 'active'   // ❌ returns NOTHING
$filter=status eq 'Active'   // ✅ matches

Full-text search (search=) lower-cases via the analyzer, so it "just works". But $filter, $orderby, facets & keys do byte-exact comparisons.

The fix - two options

  1. Normalize on write: lower-case values in your data loader (deterministic, works everywhere, no query change).
  2. Normalizers (index-side): attach a normalizer to filterable/sortable fields so Azure lower-cases at filter time.
"normalizers": [{
  "name": "lowercase_norm",
  "@odata.type": "#Microsoft.Azure.Search.CustomNormalizer",
  "tokenFilters": ["lowercase"]
}]
Best practice

Do both: normalize in the loader for predictable data, and add a lowercase normalizer as a safety net for ad-hoc writes.

03 · The Key Field

Why you shouldn't "search" the Id key - & its constraints

Every index needs exactly one key field (usually Id). It uniquely identifies a document and drives merge/upload/delete - but it is a poor search target.

Hard constraints on the key field

RuleDetail
TypeMust be Edm.String.
CardinalityExactly one key per index.
UniquenessMust be unique - it's the document identity.
Allowed charsLetters, digits, _, -, = only. No spaces, /, #, unicode, etc.
Facets/SortKey cannot be facetable; sortable is limited/pointless.
EmptyCannot be null or empty.

Why not full-text search on it?

  • It's typically a GUID/opaque code - no linguistic meaning to tokenize.
  • To fetch by id, use the direct Lookup API - it's O(1) and avoids scoring overhead.
  • To filter by id, use $filter=Id eq '...' (exact) not search=.
GET /indexes/opportunities/docs/'op-1024'?api-version=2024-07-01
// Direct key lookup - fastest way to get one document
Encoding tip

If your natural id has illegal chars (e.g. an email or path), Base64-URL encode it before storing as the key, and keep the original in a separate searchable field.

04 · Schema

Field data types & parameters - with examples

Why are they called “EDM” data types?

EDM = Entity Data Model - the type system defined by the OData protocol that Azure AI Search's REST API is built on. Because every type name is prefixed with the EDM namespace (e.g. Edm.String, Edm.Int32), they are language-neutral and map cleanly to JSON over the wire - independent of C#, Java or Python client types.

05 · Under the Hood

How full-text & fuzzy search work behind the scenes

Indexing pipeline (write time)

  1. Char filters - clean raw text (strip HTML, map chars).
  2. Tokenizer - split into tokens ("Acme-Corp" → "Acme", "Corp").
  3. Token filters - lowercase, remove stop-words, stem ("running"→"run").
  4. Resulting terms go into the inverted index: term → list of docs.

Query time

The query text runs through the same analyzer, then matched terms are looked up in the inverted index, and results are ranked with BM25.

BM25 relevance - the intuition

  • TF: more occurrences of the term → higher score (with diminishing returns).
  • IDF: rare terms across the corpus count more than common ones.
  • Field length: a hit in a short field (title) outweighs one in a long field (description).

Fuzzy search (~ typo tolerance)

Uses edit distance (Levenshtein), max 2. search=Amce~ matches "Acme". Requires queryType=full (Lucene syntax).

// up to 1 edit
search=opportunty~1&queryType=full
Wildcard vs fuzzy

micro* = prefix wildcard. micro~ = fuzzy. Wildcards are not analyzed (no stemming), so use with care.

06 · Text Analysis

Analyzers - built-in catalog, defaults vs custom

An analyzer is the full text-processing chain (char filters → tokenizer → token filters). It decides how a field is searched. The same analyzer is applied at index time and query time. Every searchable string field uses one - the default is standard.lucene unless you override it.

Readily available (in-built) analyzers - reference by name, zero config

Analyzer nameWhat it doesGood for
standard.lucene defaultGrammar-based split, lowercased, light punctuation removal.General text.
standardasciifolding.luceneStandard + folds accents (café→cafe).Accented / multilingual names.
keywordEntire field value = one token (no splitting).Codes, SKUs, ids, enums.
whitespaceSplits only on whitespace; keeps case & symbols.Tags, symbols like C#.
simpleSplits on non-letters, lowercases; drops digits.Simple alphabetic text.
stopLike simple + removes English stop-words.Short prose, no stemming.
patternSplits by a regex (default \W+).Emails, paths, custom delimiters.
[lang].microsoftMicrosoft NLP: lemmatization + stop-words (50+ langs, e.g. en.microsoft, fr.microsoft).High-quality language search.
[lang].luceneLucene language analyzer: stemming + stop-words (e.g. en.lucene).Open-source language search.

Configure a default (built-in) analyzer

Just name it - nothing to define elsewhere.

{ "name":"description", "type":"Edm.String",
  "searchable":true,
  "analyzer":"en.microsoft" }

// Different analyzer at index vs query time
{ "name":"name", "type":"Edm.String", "searchable":true,
  "indexAnalyzer":"edge_analyzer",   // build prefixes
  "searchAnalyzer":"standard.lucene" }  // match whole words
Immutable

Changing a field's analyzer needs a rebuild (or a new field). You can't retro-analyze existing docs in place.

Configure a custom analyzer

Define once under index.analyzers[], then reference the name from a field. A custom analyzer = 0..n charFilters + 1 tokenizer + 0..n tokenFilters.

{
  "name":"opportunities",
  "fields":[
    { "name":"name", "type":"Edm.String",
      "searchable":true, "analyzer":"opp_custom" }
  ],
  "analyzers":[{
    "name":"opp_custom",
    "@odata.type":"#Microsoft.Azure.Search.CustomAnalyzer",
    "charFilters":["html_strip"],
    "tokenizer":"standard_v2",
    "tokenFilters":["lowercase","asciifolding"]
  }]
}
Test before you commit
POST /indexes/opportunities/analyze?api-version=2024-07-01
{ "text":"The Running Foxes-2024", "analyzer":"opp_custom" }
// → running, foxes, 2024   (inspect tokens per field)
Default vs custom - the rule

Default/built-in: reference by name ("analyzer":"keyword") - nothing to declare. Custom: declare it in analyzers[] with an @odata.type + unique name, then point the field at that name.

07 · Text Analysis

Tokenizers - built-in catalog, defaults vs custom

The tokenizer is the heart of an analyzer: it decides where raw text is broken into tokens. A custom analyzer uses exactly one tokenizer; everything downstream operates on its output.

Use a default tokenizer (by name)

No-config tokenizers are referenced directly inside a custom analyzer.

"analyzers":[{
  "name":"code_analyzer",
  "@odata.type":"#Microsoft.Azure.Search.CustomAnalyzer",
  "tokenizer":"keyword_v2",       // built-in, no definition
  "tokenFilters":["lowercase"]
}]

Define a custom (configured) tokenizer

Configurable tokenizers must be declared in tokenizers[], then referenced by name.

"tokenizers":[{
  "name":"edge_tok",
  "@odata.type":"#Microsoft.Azure.Search.EdgeNGramTokenizer",
  "minGram":2, "maxGram":15,
  "tokenChars":["letter","digit"] }],
"analyzers":[{
  "name":"edge_analyzer",
  "@odata.type":"#Microsoft.Azure.Search.CustomAnalyzer",
  "tokenizer":"edge_tok",          // your named tokenizer
  "tokenFilters":["lowercase"] }]
Why per field?

Autocomplete/prefix fields want edgeNGram; SKUs/codes want keyword_v2; URLs/emails want uax_url_email; prose wants standard_v2.

08 · Text Analysis

Token filters - built-in catalog, defaults vs custom

Token filters run after the tokenizer, in order, transforming the token stream: lowercasing, stemming, stop-word removal, synonyms, n-grams, folding, deduping. An analyzer can chain many of them.

Use default token filters (by name)

No-config filters chain directly - order matters (left → right).

"analyzers":[{
  "name":"folded",
  "@odata.type":"#Microsoft.Azure.Search.CustomAnalyzer",
  "tokenizer":"standard_v2",
  "tokenFilters":["lowercase","asciifolding","porter_stem"]
}]

Define custom (configured) token filters

Parameterized filters go in tokenFilters[] and are referenced by name.

"tokenFilters":[
  { "name":"my_stop",
    "@odata.type":"#Microsoft.Azure.Search.StopwordsTokenFilter",
    "stopwords":["inc","ltd","corp"] },
  { "name":"my_syn",
    "@odata.type":"#Microsoft.Azure.Search.SynonymTokenFilter",
    "synonyms":["laptop, notebook","vm => virtual machine"] }
],
"analyzers":[{
  "name":"opp_text",
  "@odata.type":"#Microsoft.Azure.Search.CustomAnalyzer",
  "tokenizer":"standard_v2",
  "tokenFilters":["lowercase","my_syn","my_stop"]
}]
Why per field?

Filter/exact fields often need only lowercase; description fields benefit from stemming + stopwords + synonyms for recall. Order matters - stem after lowercasing, stop before synonyms if you want clean expansion.

09 · Text Analysis

Char filters - built-in catalog, defaults vs custom

Char filters run first - before the tokenizer - operating on the raw character stream to clean or normalize input so meaningful symbols aren't lost during tokenizing. An analyzer can chain several.

Readily available (in-built) char filters

Char filter@odata.typeWhat it doesConfig?
html_strip(predefined name)Strips HTML tags & decodes entities from stored markup.No
mappingMappingCharFilterLiteral char/string replacements you supply.Yes
pattern_replacePatternReplaceCharFilterRegex find/replace over raw text.Yes

Azure ships one no-config char filter (html_strip); the other two are templates you must configure as named instances. There are only these three char-filter types.

Use the default (built-in) char filter

Reference html_strip by name - no definition needed.

"analyzers":[{
  "name":"clean_html",
  "@odata.type":"#Microsoft.Azure.Search.CustomAnalyzer",
  "charFilters":["html_strip"],   // built-in
  "tokenizer":"standard_v2",
  "tokenFilters":["lowercase"]
}]
// "<p>Big &amp; Bold</p>" → big, bold

Define custom char filters (configured)

Declare in charFilters[], then reference from the analyzer.

"charFilters":[
  { "name":"sym_map",
    "@odata.type":"#Microsoft.Azure.Search.MappingCharFilter",
    "mappings":["C#=>csharp","C++=>cplusplus","&=>and"] },
  { "name":"strip_dashes",
    "@odata.type":"#Microsoft.Azure.Search.PatternReplaceCharFilter",
    "pattern":"[-_]", "replacement":" " }
],
"analyzers":[{
  "name":"symbol_safe",
  "@odata.type":"#Microsoft.Azure.Search.CustomAnalyzer",
  "charFilters":["sym_map","strip_dashes"],
  "tokenizer":"standard_v2",
  "tokenFilters":["lowercase"] }]
Order matters

char filter → tokenizer → token filters. Without sym_map, the standard tokenizer drops # so "C#" collapses to "c". Mapping before tokenizing preserves the intent as "csharp".

10 · Relevance

Scoring profiles - tune relevance & boosting

A scoring profile adjusts the base BM25 score using field weights, freshness, distance, magnitude or tag boosts - so business priorities shape ranking.

Definition

"scoringProfiles":[{
  "name":"boostRecentBigDeals",
  "text":{ "weights":{ "name":5, "description":1 } },
  "functions":[
    { "type":"magnitude", "fieldName":"amount",
      "boost":3,
      "magnitude":{ "boostingRangeStart":0, "boostingRangeEnd":100000 } },
    { "type":"freshness", "fieldName":"createdOn",
      "boost":2, "freshness":{ "boostingDuration":"P30D" } }
  ]
}]

Apply it in a query

POST /indexes/opportunities/docs/search
{ "search":"cloud migration",
  "scoringProfile":"boostRecentBigDeals" }

Function types

magnitudefreshnessdistancetag

Why per field

Weights are set per searchable field; functions target specific numeric/date/geo/collection fields.

Set a default

Add "defaultScoringProfile":"..." on the index so every query benefits without changing client code.

11 · UX

Suggesters - help people while they type

Use a suggester when you want the app to help people while they type, like the search box on Amazon or the contact search on a phone. It shows likely matches before the user finishes typing.

Think of it like this

The app remembers the most likely names or titles that start with the letters you typed. Instead of forcing the user to guess the exact full name, it offers a short list of likely matches.

When to use it

  • Product search: type mic and show Microsoft products.
  • Customer lookup: type con and show matching company names.
  • Project search: type pro and show project titles.

What the user sees

Typed lettersHelpful suggestion
micMicrosoft Surface, Micro Focus, Micron
contContoso Retail, Contoso Cloud
proProject Orion, Professional Services

How it works

1. Type a few letters

The user starts typing part of a name, product, or company.

2. Show likely matches

The app suggests a short list of close matches instead of making the user guess.

3. User picks one

The user taps or clicks the right suggestion and continues faster.

Best fit

Names, titles, codes, company names, product names, and other short labels people recognize while typing.

Not for

Full document search, filters, exact reports, or long descriptions. Those should use normal search and filtering.

In one sentence

A suggester is the feature that says, “Did you mean one of these?” while the user is still typing.

12 · UX

How the queries look - suggest and autocomplete

These are the two common ways people use suggesters. One helps finish the word in the search box, the other shows a short list of matching records.

/autocomplete - finish the word

Use this when the user is still typing and you want to complete the search phrase itself.

GET /indexes/opportunities/docs/autocomplete?search=mic&suggesterName=sg&autocompleteMode=oneTerm&api-version=2024-07-01

// sample output
{
  "text": "microsoft",
  "queryPlusText": "mic microsoft"
}

Example use

  • User types mic.
  • The app suggests microsoft.
  • The search box becomes easier and faster to finish.

/suggest - show matching items

Use this when you want to show a small list of matching records that the user can pick from.

GET /indexes/opportunities/docs/suggest?search=contoso&suggesterName=sg&$top=10&api-version=2024-07-01

// sample output
{
  "value": [
    { "@search.score": 0.92, "name": "Contoso Retail" },
    { "@search.score": 0.88, "name": "Contoso Cloud" }
  ]
}

Example use

  • User types cont.
  • The app shows matching company names.
  • The user chooses the right record from the list.
Easy rule

/autocomplete helps finish the text. /suggest helps choose the item.

13 · Schema Discipline

Searchable · Filterable · Sortable · Retrievable

These four attributes drive both capability and index size/cost. Enable only what you truly query - every extra flag inflates storage and build time.

AttributeEnablesApplies toConstraint / cost
searchableFull-text search=Strings & string collections onlyBuilds inverted index → largest storage impact.
filterable$filter, $countAll typesExact, case-sensitive; needed for facets too.
sortable$orderbySimple fields; not collectionsComplex/collection fields can't be sortable.
retrievableReturned in resultsAll typesTurn off for secret/internal fields; still searchable.

Design heuristics

  • Ids/codes: filterable + retrievable, not searchable.
  • Descriptions: searchable + retrievable, not filterable/sortable.
  • Status/category: filterable + facetable.
  • Numbers/dates: filterable + sortable.
Mutability

You can turn retrievable on/off anytime. Turning on searchable/filterable/sortable/facetable that were previously off requires a field rebuild - so decide early.

Cost lever

An index where every field has every flag can be 3-5× larger. Trim aggressively; it speeds up indexing and lowers tier requirements.

14 · Governance

Index lifecycle & change restrictions

What you CAN change without rebuild

  • ➕ Add new fields (existing docs get null for them).
  • Toggle retrievable.
  • Add/modify scoring profiles, CORS, synonym map references.
  • Add suggesters? ❌ - needs rebuild.

What FORCES a rebuild (drop + recreate)

  • Delete or rename a field.
  • Change a field's type or analyzer.
  • Turn on searchable/filterable/sortable/facetable.
  • Change the key field.

Safe evolution pattern

  1. Create index-v2 with the new schema.
  2. Bulk re-index data into v2.
  3. Swap an alias from v1 → v2 (zero-downtime cutover).
  4. Delete v1 once validated.
Index aliases

Aliases let clients query a stable name (opportunities) while you rebuild behind it. This is the professional way to handle breaking schema changes.

15 · Querying

OData $filter - building filter queries

Filters are exact, case-sensitive boolean expressions evaluated over filterable fields. They include/exclude documents but do not affect relevance score.

Operators & logic

// comparison
$filter=amount gt 50000 and status eq 'won'

// grouping + or
$filter=(status eq 'won' or status eq 'open')
        and amount ge 1000

// date range
$filter=createdOn ge 2026-01-01T00:00:00Z
        and createdOn lt 2026-07-01T00:00:00Z

Collections & functions

// any/all over a collection field
$filter=tags/any(t: t eq 'priority')
$filter=tags/all(t: t ne 'archived')

// string functions
$filter=search.ismatch('cloud','name')
$filter=geo.distance(location, geography'POINT(-122 47)') lt 10
Full request (Postman)
POST /indexes/opportunities/docs/search?api-version=2024-07-01
{ "search":"*",
  "filter":"amount gt 50000 and status eq 'won'",
  "count":true }
16 · Querying

OData search - the query text

The search parameter is the actual text matched against searchable fields. Combine it with searchFields to scope, and $filter to pre-narrow.

// simple query, all searchable fields
{ "search":"cloud migration" }

// scope to specific fields + weight order
{ "search":"migration",
  "searchFields":"name,description" }

// search + filter + select + count
{ "search":"azure",
  "filter":"status eq 'open'",
  "select":"Id,name,amount",
  "count":true }

search vs filter - remember

  • search = linguistic, ranked, case-insensitive.
  • filter = exact, boolean, case-sensitive, unranked.
  • Use filter to narrow, search to rank.
Match-all

"search":"*" matches every document - useful when you only want to filter/sort/browse.

17 · Querying

Full-text search with Lucene syntax

Set queryType=full to unlock the Lucene grammar: boolean operators, fielded search, wildcards, fuzzy, proximity, boosting & regex.

FeatureExample
Booleancloud AND (aws OR azure) NOT legacy
Fieldedname:migration
Phrase"digital transformation"
Wildcardmigrat*
Fuzzyopportunty~1
Proximity"cloud cost"~5
Boostazure^3 aws
Regex/op-[0-9]{4}/
{ "search":"name:(cloud AND migrat*) NOT legacy",
  "queryType":"full",
  "searchMode":"all" }
Escaping

In Lucene syntax these are special: + - && || ! ( ) { } [ ] ^ " ~ * ? : \ /. Escape with a backslash to search them literally.

Simple vs full

Default queryType=simple supports + | - " * ( ). Switch to full only when you need the advanced operators above.

19 · Querying

$orderby, $top/$skip & their limits

Ordering

// multi-key sort, asc/desc
{ "orderby":"amount desc, name asc" }

// by relevance then recency
{ "search":"cloud",
  "orderby":"search.score() desc, createdOn desc" }

// by geo distance
{ "orderby":"geo.distance(location, geography'POINT(-122 47)') asc" }

Paging & size limits

ParamLimit
$topMax 1000 per page.
$skipMax 100,000; deep paging is slow.
orderby fieldsUp to 32 clauses.
{ "search":"*", "top":25, "skip":50,
  "orderby":"createdOn desc" }
Deep paging

For exports beyond ~100k, don't use $skip. Page by a filter on a sortable key (range paging) or use the push-based export pattern.

20 · Response Shape

$select vs full query - JSON output difference

Full result (all retrievable fields)

{
  "@odata.count": 128,
  "value": [
    {
      "@search.score": 4.21,
      "Id":"op-1024",
      "name":"Cloud Migration",
      "status":"open",
      "amount":75000,
      "description":"...",
      "createdOn":"2026-05-01T..."
    }
  ]
}

With "select":"Id,name,amount"

{
  "@odata.count": 128,
  "value": [
    {
      "@search.score": 4.21,
      "Id":"op-1024",
      "name":"Cloud Migration",
      "amount":75000
    }
  ]
}
Key differences

@search.score & @odata.* metadata are always present. $select only trims the document fields - smaller payload, faster network, lower serialization cost. It does not change scoring or which docs match.

21 · Advanced Filter

What is search.ismatch for?

It lets you run a full-text search inside a $filter expression - mixing ranked text matching with boolean filter logic. It is not a pagination tool.

Signatures

// search.ismatch(search, [fields], [queryType], [mode])
$filter=search.ismatch('cloud','name')

// scoring variant contributes to relevance
$filter=search.ismatchscoring('azure','name,description','full','any')

Powerful "OR across search+filter"

// name matches 'cloud' OR amount > 100k
$filter=search.ismatch('cloud','name')
        or amount gt 100000

ismatch vs ismatchscoring

  • search.ismatch → pure boolean, no score impact.
  • search.ismatchscoring → contributes to @search.score.
Not for pagination

Pagination is done with $top/$skip (or range paging). search.ismatch exists to combine full-text relevance with structured filter logic in one expression.

22 · Sorting Internals

How & where $orderby is performed

Where it runs

  • Sorting executes on the search service, on the shards, after matching but before paging ($top/$skip).
  • Default order (no $orderby) is by relevance = search.score() desc.
  • When you specify $orderby, relevance is replaced unless you include search.score() desc explicitly.

Constraints

RuleDetail
Field flagMust be sortable = true.
TypesSimple types only - not collections or complex fields.
Special funcssearch.score() & geo.distance() allowed.
Clause countUp to 32 sort clauses.
Null handlingNulls sort first on asc, last on desc.
Tie-breaking

Always add a stable secondary key (e.g. Id asc) so equal primary values page deterministically.

Updating a field & the error you'll see

If you attempt a disallowed field change (e.g. flip filterable from false→true, or change type), the API rejects it. Here's the exact shape to expect.

The attempted change

PUT {{base}}/indexes/opportunities?api-version=2024-07-01
{ /* status field changed from filterable:false → true */

}

Error response 400

{
  "error":{
    "code":"",
    "message":"Existing field 'status' cannot be changed. Set 'allowIndexDowntime=true' or rebuild the index."

}
Fix

Either rebuild via an alias swap, or (for analyzer-only changes) retry with ?api-version=2024-07-01&allowIndexDowntime=true.

DELETE the entire index

DELETE {{base}}/indexes/opportunities?api-version=2024-07-01
api-key: {{admin-key}}

Response 204 No Content on success, 404 if it doesn't exist.

Irreversible

This drops the schema and all documents instantly. There is no soft-delete or recycle bin. Always snapshot the schema (GET the index definition) and have a re-index plan before deleting in any shared environment.

Safer alternative - clear documents, keep schema

To empty an index without dropping it, delete documents in batches by key. Or rebuild via alias swap and delete the old index only after cutover.

36 · Edge Cases

Special characters in Azure Search filters

Special characters get stripped by tokenizers (search) or must be escaped (filters). The goal: ensure user input like O'Brien, A&B, 50% isn't silently discarded.

In $filter string literals

  • Single quote ' → double it: 'O''Brien'.
  • Other chars are literal inside quotes (no HTML/URL meaning) - but the whole URL must be URL-encoded.
// name = O'Brien & Sons
$filter=name eq 'O''Brien & Sons'

In search (Lucene) queries

Escape reserved chars with \:

// reserved: + - && || ! ( ) { } [ ] ^ " ~ * ? : \ /
search="C\+\+ developer"&queryType=full
Preserve at index time

Use a mapping char filter (C#=>csharp, &=>and) or a keyword analyzer so meaningful symbols survive tokenizing instead of being dropped.

Golden rule

URL-encode the whole query string, double single-quotes in filter literals, and backslash-escape Lucene specials in search. Do those three and special characters won't get lost.

38 · Reference

The search.in / in operator for ranges & lists

To test membership against a set of values, use search.in - far cleaner and faster than chaining many or clauses.

List membership

// status in a set
$filter=search.in(status, 'won,open,negotiating')

// custom delimiter (values contain commas)
$filter=search.in(region, 'EMEA|APAC|NA', '|')

Id set membership

$filter=search.in(Id, 'op-1,op-2,op-3')

Ranges vs sets

search.in checks a discrete set. For a continuous range of ids/values use comparison operators:

$filter=Id ge 'op-1000' and Id le 'op-1999'

(String range works lexicographically - pad numeric ids for correct ordering.)

Why use it

search.in scales to thousands of values in one filter and is optimized internally - ideal for "these 500 account ids" style queries.

39 · Security

Admin key vs Query key - which for what?

API keys are passed in the api-key header. Admin keys can do everything (read + write + manage). Query keys are read-only and safe to ship to clients/browsers.

OperationKey
Create / update / delete indexAdmin
Upload / merge / delete documentsAdmin
Create indexers, data sources, skillsetsAdmin
Search / suggest / autocompleteQuery
Lookup a document by keyQuery
Golden rule

Never embed an admin key in front-end / mobile code. Use a query key there (or better, RBAC + backend proxy). There are up to 2 admin keys (for rotation) and up to 50 query keys per service.

Postman - write needs Admin key

POST {{base}}/indexes/opportunities/docs/index?api-version=2024-07-01
Content-Type: application/json
api-key: {{admin-key}}      // ✅ admin required to write
{ "value":[ { "@search.action":"mergeOrUpload",
  "Id":"op-1", "status":"won" } ] }

Postman - read uses Query key

POST {{base}}/indexes/opportunities/docs/search?api-version=2024-07-01
Content-Type: application/json
api-key: {{query-key}}      // ✅ query key is enough to search
{ "search":"cloud", "select":"Id,name" }
Wrong key = 403

Using a query key for a write returns 403 Forbidden. Get keys via the portal or the Management API; rotate the second admin key with zero downtime.

40 · Automation

Indexers - automated data ingestion

An indexer is a managed crawler that pulls data from a supported data source (Azure SQL, Cosmos DB, Blob/ADLS, Table Storage) and pushes it into an index - on demand or on a schedule - with change tracking, so you don't hand-code the "push" pipeline.

Three pieces to wire up

  1. Data source - where the data lives + change-detection policy.
  2. Index - the target schema.
  3. Indexer - maps source → index fields, schedule, options.

1 · Create the data source

POST {{base}}/datasources?api-version=2024-07-01
api-key: {{admin-key}}
{ "name":"opp-sql-ds",
  "type":"azuresql",
  "credentials":{ "connectionString":"{{sql-conn}}" },
  "container":{ "name":"Opportunities" },
  "dataChangeDetectionPolicy":{
    "@odata.type":"#Microsoft.Azure.Search.HighWaterMarkChangeDetectionPolicy",
    "highWaterMarkColumnName":"rowVersion" } }

2 · Create the indexer (schedule)

POST {{base}}/indexers?api-version=2024-07-01
api-key: {{admin-key}}
{ "name":"opp-indexer",
  "dataSourceName":"opp-sql-ds",
  "targetIndexName":"opportunities",
  "schedule":{ "interval":"PT1H" },   // hourly
  "fieldMappings":[
    { "sourceFieldName":"OpportunityId", "targetFieldName":"Id" } ] }

3 · Run & monitor

// run now (on demand)
POST {{base}}/indexers/opp-indexer/run?api-version=2024-07-01
// check status / last result / errors
GET  {{base}}/indexers/opp-indexer/status?api-version=2024-07-01
// reset (force full re-index next run)
POST {{base}}/indexers/opp-indexer/reset?api-version=2024-07-01
Push vs Pull

Indexer (pull) = zero-code, scheduled, change-tracked - best for DB/Blob sources. Push API (/docs/index) = full control, real-time, any source - best for custom apps & event-driven sync.

Enable / disable

An indexer runs on its schedule once created. Pause it with "disabled": true in its definition; deletions need a soft-delete change detection policy so removed rows are also removed from the index.

41 · Round-up

Things often missed - with examples

🔑 Keys & security

Admin key = full control (writes). Query key = read-only. Prefer RBAC / managed identity over keys in production; scope query keys to the client.

🌐 CORS

Browser apps calling Search directly need corsOptions.allowedOrigins on the index. Never embed an admin key in front-end code.

🔁 Synonym maps

Create a synonym map (laptop, notebook) and attach to a field's synonymMaps - expands recall without re-indexing text.

🧮 Complex types

Model nested objects/arrays (line items, addresses). Filter with field/subfield and any/all.

📈 Monitoring

Watch /indexes/{name}/stats for doc count & storage; enable diagnostic logs for throttling & latency.

42 · Playbook

Design & operations best practices

Schema

  • Enable only the attributes each field actually needs (cost & speed).
  • Normalize filter/sort strings to lower-case (loader + normalizer).
  • Never make the key searchable; keep ids opaque & encoded.
  • Pick analyzers per field intent (keyword vs language vs ngram).

Querying

  • Filter to narrow, search to rank; add $select to trim payloads.
  • Always add a tie-break sort key (Id asc).
  • Use search.in for large value sets; avoid deep $skip.

Operations

  • Batch writes (~1000 docs); handle 207/503 with retry & backoff.
  • Snapshot the index definition before any destructive change.
  • Use RBAC/managed identity; keep admin keys server-side only.
One-line summary

Model fields for their job, analyze text intentionally, filter+rank deliberately, and evolve indexes behind an alias.
